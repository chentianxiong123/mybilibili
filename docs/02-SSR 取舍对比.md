# SSR 取舍对比：为什么你的页面不需要服务端渲染

## 前言

在 Nuxt/Next.js 这类"全栈框架"中，SSR 是默认选项。但默认不等于最优。本文从实际项目经验出发，对比 SSR 和 CSR 的优劣，给出按路由选择渲染策略的决策框架。

## 渲染策略对比

| 维度 | CSR | SSR | SSG |
|------|-----|-----|-----|
| SEO | ❌ 差 | ✅ 好 | ✅ 最好 |
| 首屏速度 | ❌ 慢（等 JS 加载完才渲染） | ✅ 快（HTML 直出） | ✅ 最快（CDN 直达） |
| 服务端成本 | 无 | 高（每次请求占 CPU） | 仅构建时 |
| 内容新鲜度 | 实时 | 实时 | 构建时冻结 |
| 交互复杂度 | 无限制 | 受 hydration 限制 | 受 hydration 限制 |
| 调试难度 | 低 | 高（hydration 经常出问题） | 低 |
| 冷启动 | 无 | 有（Node 冷启动） | 无 |

## 核心问题：为什么 SSR 容易出问题

### 1. 环境差异

服务端渲染时没有：
- `window` / `document` / `localStorage`
- `ResizeObserver` / `IntersectionObserver`
- 用户登录态（localStorage 中的 token）

任何依赖这些的代码在 SSR 中都会报错或产生不一致。

### 2. Hydration 陷阱

SSR 生成完整 HTML，客户端 Vue 重新"激活"（hydration）。如果两个阶段生成的 DOM 树不一致，Vue 报错并丢弃服务端渲染的 DOM，重新在客户端渲染——**首屏优势完全丧失**。

典型陷阱：
- `v-if` 依赖登录态 → 服务端不渲染，客户端渲染
- `Math.random()` / `Date.now()` → 服务端和客户端值不同
- 第三方库直接操作 DOM → 服务端无 DOM 可用

### 3. 性能开销

SSR 是 CPU 密集型的。B站早期 SSR 文章提到：一个首页渲染请求需要 200ms 的服务端计算时间。对比 CSR 直接在 CDN 上返回静态 HTML，SSR 对服务器压力大得多。

## 决策框架：你的页面需要 SSR 吗？

### 需要 SSR 的场景（问自己三个问题）

1. **搜索引擎需要收录这个页面吗？**  
   - 首页、视频详情页、分类页 → 需要 SEO → SSR  
   - 个人中心、动态流、私信 → 不需要 SEO → 不用 SSR  

2. **页面内容是否依赖用户登录态？**  
   - 完全依赖 → 不适合 SSR（服务端无法渲染正确的版本）  
   - 主体公开 + 少量交互 → 可以 SSR + 局部处理  

3. **页面的首屏速度是否关键？**  
   - 营销页、落地页 → 关键 → SSR  
   - 后台管理页、仪表盘 → 不关键 → CSR  

### 决策矩阵

| 页面类型 | 需要 SEO? | 依赖登录态? | 首屏关键? | 推荐策略 |
|----------|-----------|------------|-----------|---------|
| 首页 | ✅ | ❌ | ✅ | SSR |
| 视频详情 | ✅ | ❌(仅交互) | ✅ | SSR |
| 搜索/分类 | ✅ | ❌ | ✅ | SSR |
| 用户主页 | ✅ | ❌(半公开) | ✅ | SSR 或 CSR |
| 动态流 | ❌ | ✅ | ❌ | CSR |
| 个人中心 | ❌ | ✅ | ❌ | CSR |
| 私信 | ❌ | ✅ | ❌ | CSR |
| 直播 | ❌ | ✅(实时) | ❌ | CSR |
| 创作中心 | ❌ | ✅ | ❌ | CSR |

## 行业做法

### B站（2017 年技术文章）

> 对于不需要 SEO 的页面，是一个不错的方式。前端开发完成之后，通过 webpack 打包出对应的 js 和 css 上传到 CDN 上面，然后将引用了对应的资源的 html 文件上传到静态机。  
> 现在还有一些页面仍然是这种模式，例如：`/account/history`。

B站的做法：**首页部分 SSR（右边 SSR，左边 CSR），历史记录页纯 CSR**。

### 有赞

> 部分模块（不需要 SSR 的模块）客户端渲染 — 因为服务端渲染是 CPU 密集型操作，非首屏的模块或者不重要的模块完全可以采用客户端渲染。

有赞的做法：**一个页面内也不是全部 SSR，非首屏模块用 CSR**。

### 闲鱼

> 当 SSR 应用不可用时，页面能够自动降级到稳定的 CSR 模式。

闲鱼的做法：**SSR + CSR 双链路，SSR 失败自动降级**。

## 结论

### 不要"全有或全无"

最大的错误是给整个应用选一个渲染策略。不同页面有不同需求，按路由选择策略才是正确的。

### 混合渲染是标准答案

```ts
routeRules: {
  // 公开内容页 — SSR（SEO 收益）
  '/': { ssr: true },
  '/manuscript/**': { ssr: true },

  // 私有页面 — CSR（避免 hydration 问题）
  '/dynamic/**': { ssr: false },
  '/profile/**': { ssr: false },
  '/personal-center/**': { ssr: false },
}
```

### 记住三点

1. SSR 不是"高级模式"，它是有代价的优化手段
2. 不需要 SEO 的页面关掉 SSR，减少 90% 的 hydration 问题
3. B站、有赞、闲鱼都这么做，你不是在"偷懒"
