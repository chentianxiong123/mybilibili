# 移动端方案对比：性能 vs UI 准确度

## 三个方案

| 方案 | 项目 | 现状 |
|---|---|---|
| **WebView 包装** | `mybilibili-wap`（Vite + Vue 3 SPA） | 未做原生包装，纯浏览器 |
| **Flutter** | `mybilibili-app-flutter` | 已放弃（构建环境问题） |
| **NativeScript-Vue** | `mybilibili-ns` | 当前主力，APK 已装到 Waydroid |

## 对比维度

### 1. 渲染性能

| 场景 | WebView | Flutter | NativeScript-Vue |
|---|---|---|---|
| **页面滚动** | WebView 滚动由浏览器引擎处理，60fps 流畅但偶有白块（Android WebView 版本差异大） | Skia 自绘引擎，60fps 极稳，但首次渲染需等框架初始化 | 原生 `ScrollView` / `ListView`，系统级 RecyclerView，丝滑且无白块 |
| **视频播放** | hls.js + MediaSource Extensions，CPU 软解多，发热高 | 原生 ExoPlayer 硬解，省电低发热 | WebView 嵌入（用同一套 hls.js），视频播放器本身无差异 |
| **弹幕叠加** | Canvas 2D 渲染弹幕，性能与帧率成正比 | 需自定义 CustomPainter 实现 | artplayer-plugin-danmuku 在 WebView 中 Canvas 渲染，性能同 WebView |
| **列表虚拟化** | 浏览器没有原生虚拟列表，长列表 DOM 节点多会卡 | `ListView.builder` 只构建可见项，万级列表流畅 | `ListView` 底层 RecyclerView，Android 原生虚拟化，万级列表丝滑 |
| **启动速度** | 加载 HTML + JS + CSS 后再渲染，首屏 1-3s | 引擎初始化 + Dart VM 启动，冷启动 2-5s | NativeScript 运行时初始化 + V8 引擎，冷启动 1-2s |
| **内存占用** | 浏览器进程本身占用 ~100MB，再加页面 DOM | ~50MB（release）+ Skia 纹理内存 | ~30MB（release），原生控件轻量 |

**结论**：NativeScript-Vue 在滚动和列表场景下性能最好（原生控件），WebView 和 Flutter 各有劣势。

### 2. UI 准确度

| 场景 | WebView | Flutter | NativeScript-Vue |
|---|---|---|---|
| **控件一致性** | 网页 `div` 模拟按钮、输入框，不同 Android 版本 WebView 样式不一致 | 自绘控件，所有平台一模一样，但不像原生 | 真实的 `android.widget.Button`、`EditText`，系统组件，100% 一致 |
| **系统字体** | 网页 CSS 字体栈，可能和系统字体不同 | Skia 渲染，字体文件和系统分离 | 原生 `android:fontFamily`，与系统字体完全一致 |
| **无障碍** | ARIA 标签 + 语义化 HTML，支持度有限 | 自绘控件无障碍需额外实现，易遗漏 | 原生控件自带无障碍支持，TalkBack 开箱即用 |
| **输入法** | 网页 `input` 元素，键盘弹出/收起由 WebView 控制，偶有布局错位 | 自绘 TextField 与系统输入法桥接，偶有光标位置不准确 | 原生 `EditText`，输入法行为与系统完全一致 |
| **深色模式** | CSS `prefers-color-scheme` 媒体查询 | 需手动监听系统主题切换 | 原生 `Configuration.UI_MODE_NIGHT_YES`，自动跟随系统 |
| **手势交互** | 触摸事件由浏览器处理，`touchstart` → `touchend`，有 300ms 延迟风险 | GestureDetector 自绘处理，行为与平台一致 | 原生 `onTouchListener`，系统级手势识别，无延迟 |
| **通知栏/状态栏** | 无控制权 | 可以控制，但边缘情况多 | 原生 `ActionBar` + 状态栏，系统级 |
| **屏幕适配** | CSS `rem` / `vw` 响应式，但不同屏幕比例下布局可能崩 | 逻辑像素 + MediaQuery，适配灵活 | 原生 `dp` + 布局容器，不同屏幕尺寸自动适配，但复杂布局代码量更大 |

**结论**：NativeScript-Vue 在 UI 准确度上全面领先，因为每个控件都是真实的 Android 原生组件。Flutter 的自绘方案在跨平台一致性上占优，但"不像原生"。WebView 的模拟最不稳定。

## 对我们项目的实际意义

**首页信息流**（推荐视频列表、分类 TabBar）：
- NativeScript 的 `ListView` + 原生滚动 > Flutter 的 `ListView.builder` > WebView 的 DOM 列表
- 滚动体验是用户最敏感的维度，NativeScript 胜出

**视频播放器**：
- 三个方案实质相同：最终都是调用原生播放器（ExoPlayer）或 hls.js 软解
- 我们目前的 WebView 嵌入方案（player.html）在三个方案中可复用，不受框架选择影响
- 如果想优化，可以单独把播放器替换为 `@nativescript/videoplayer` 插件，获得原生硬解，但弹幕系统需要重新实现

**输入框/表单**（登录页、评论输入、搜索框）：
- WebView 的键盘弹出和布局错位是常见痛点
- NativeScript 的 `TextField` 是原生控件，无此问题
- 这个差异在日常使用中感知最明显

**结论**：NativeScript-Vue 对"信息流 App + 视频播放 + 弹幕 + 评论"这个场景来说，是性能与 UI 准确度最优的方案。Flutter 在跨平台一致性上更强，但对我们（只做 Android）来说没有额外价值。WebView 的开发成本最低，但用户体验最差。
