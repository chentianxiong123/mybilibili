## 1. 转码流程与 ffmpeg 调用位置

### 1.1 代码位置

`work-service/internal/work/transcode.go`

| 函数 | 行号 | 作用 |
|---|---|---|
| `Transcode()` | 61-90 | 视频转 HLS 分片 |
| `ExtractAudio()` | 92-102 | 提取音频 MP3 |
| `GetDuration()` | 48-58 | ffprobe 读时长 |

转码参数（当前为**纯软件编码**）：

```go
"-vf", "scale=" + scale,
"-c:v", "libx264", "-preset", "veryfast", "-crf", crf,
"-c:a", "aac", "-b:a", "128k",
"-f", "hls", "-hls_time", "6", ...
```

档位：`1080p → crf20/1920px`，`720p → crf22/1280px`，默认 `→ crf23/854px`。

调度链：`pipeline.go` 的 `Start()` 订阅 NATS `TopicVideoProcess` → `doTranscode()` 下载源文件 → 转三档 → 上传 MinIO。

调用方式为 `exec.CommandContext(ctx, "ffmpeg", args...)`，直接调 PATH 中的 `ffmpeg` 命令，无硬编码路径。**纯软件参数不依赖任何 GPU/硬件，换电脑只需安装 ffmpeg 即可，零适配成本**。

### 1.2 当前转码产物对比（实测）

| 指标 | 源视频 | 转码分片 720p |
|---|---|---|
| 合计体积 | 64 MB | 72 MB |
| 比值 | - | ~1.12x |

**关键事实**：源视频与转码分片体积接近，因为源本就是 H.264，转码是"同编码换封装"（MP4→HLS/TS），编码质量 CRF22 接近源。

## 2. 决策核心：软件编码 vs 硬件编码

### 2.1 现场实测（229 秒真实视频，720p 档）

| 指标 | 软件 libx264 (crf22) | 硬件 VAAPI (CQP22) | 结论 |
|---|---|---|---|
| 编码耗时 | 22.7 s (10.1x 实时) | 12.5 s (18.3x 实时) | 硬件快 ~1.5x |
| 产物体积 | **20.1 MB** | 39.3 MB | **软件小 1.95x** |
| 平均码率 | **738 kbps** | 1440 kbps | **软件省一半带宽** |
| 用户 CPU 时间 | **2m39s** | 33s | 软件 CPU 消耗大 4.8x |
| 换电脑兼容 | 100%（任意 ffmpeg） | 依赖 GPU 厂商/驱动 | 软件零风险 |

*注：本机 AMD Lucienne 核显 VAAPI 仅支持 CQP/CBR/VBR，不支持 ICQ 智能码率控制。*

**为什么软硬体积差这么多**：
- **软件 x264 的 CRF 模式**逐帧分析画面复杂度——静态画面给低码率、动态画面才给高码率，做到"画质恒定、总比特最少"。
- **硬编的 CQP/QP** 每帧用同一量化，对简单画面"过度花费"，总体积偏大（或因压缩率被迫降画质）。
- AV1 / H.265 软件编码在这点上更强（同画质再省 30-50%），这也是抖音/快手的编码优化方向。

### 2.2 CPU 争用与并发影响

这是软件编码被忽略的关键代价。实测数据：

| 指标 | 软件 libx264 | 硬件 VAAPI |
|---|---|---|
| 实时耗时 | 22.7 s | 12.5 s |
| 用户态 CPU 时间 | **2m39s** | 33s |
| 平均 CPU 占用 | ~7 核 | ~2.6 核 |
| 单服务并发转码 | 1 路（CPU 满） | 3~4 路（GPU 闲置） |

**问题**：
- 本机是开发/演示单机，core / ai / live / studio / search / msg-danmaku / pg / nats / minio / redis / traefik **全部跑在同一台机器上**。
- ffmpeg 软件编码会持续吃满 7 个核，导致其他服务响应变慢。
- 若同时上传多个视频，转码任务排队，每个都吃满 CPU，系统整体延迟雪上加霜。
- 硬件编码将计算卸载到 GPU 的专用 VCN 单元，CPU 几乎空闲，**不影响其他服务**。

**一句话**：软件编码在专用服务器上没问题，但在**全服务单机**环境下，CPU 争用是实实在在的瓶颈。

### 2.2 行业背景（联网核实）

**VOD 点播场景：软件编码占绝对主流（82%）**
- Streaming Learning Center（Bitmovin 2021 调查）：VOD 编码选型中软件编码占 82%（商业软件 54% + 用 FFmpeg 自建的 37%），硬件 VOD 编码器是独立细分市场。

**为什么点播用软件？**
- vBench（哥伦比亚大学）评测结论原话："**GPU 是直播转码的明显赢家，但在点播归档上牺牲压缩率和画质。**" 点播一次编码、多次播放，省下的体积就是长期的存储 + 带宽成本，编码慢几秒无所谓。

**硬编的正确打开方式是直播/实时转码**
- 硬件编码（NVENC / VAAPI / QSV / VideoToolbox）出厂为**实时编码**设计，追求速度而非画质/码率效率，因此是斗鱼、Twitch、视频会议、OBS 录屏这类实时场景的"正宗"选择。
- 直播场景为了达到实时吞吐，软件编码只能退到 veryfast/ultrafast 预设，此时硬编质量反而可能更好——这也是硬编的主场。

**唯一的例外：YouTube 的 ASIC**
- YouTube 用自研 Argos ASIC 编码大半点播视频，但那是**专门为达到软件编码质量而设计的定制芯片**（混合硬件/软件设计 + 固件持续迭代优化画质）。
- 这与消费级 GPU 附带的 NVENC/VAAPI/QSV（为实时而设计、压缩率弱于软件）完全是两回事，不可套用。

**大厂点播链条**
- B站 / 抖音 / YouTube / Netflix 的点播内容均走软件编码（x264 / x265 / SVT-AV1），仅在直播或超大规模时引入定制硬件。
- **但注意**：大厂是专用编码服务器集群，CPU 独占的；我们的转码与所有服务共居一台机器，CPU 争用客观存在。

### 2.4 决策结论（体积 vs 速度 vs CPU 并发）

| 选项 | 是否采纳 | 优缺点 |
|---|---|---|
| 现状：软件 libx264（单机共享 CPU） | ⚠️ 有代价 | 体积小、质量优（省 1.95x 带宽），但转码**吃满 ~7 核 CPU，拖慢同机其他服务** |
| **VAAPI 硬件编码 + 软件回退** | ✅ **采纳为配置项** | 快、CPU 近零负载、可并发多路；体积大 1.95x 是本机演示可接受的代价 |
| 硬件可选开关（env 切换） | ✅ | 按部署环境选择：单机演示用硬编，专用服务器用软编 |

**最终推荐方案**：
- 提供环境变量 `TRANSCODE_ENCODER=auto`（默认）选择 `vaapi` / `x264` / `auto`。
- `auto` 模式：启动时检测 `/dev/dri/renderD128` + ffmpeg 是否支持 `h264_vaapi` → 硬编；否则回退软编。**兼顾换电脑适配**。
- 默认单机演示环境用 **VAAPI**，避免转码拖垮同机其他服务；未来上专用服务器/云转码时切回软编或 x264 集群。
- 运行时转码失败自动回退软编（transcode.go 保证了硬编挂了也不影响转码）。

**实现记录**：
- `transcode.go`：`TranscodeWorker` 含 `encoder` 字段，支持 `auto`/`vaapi`/`x264`。`detectHW()` 自动探测 VAAPI 设备。`Transcode()` 硬编失败自动回退软编。
- `main.go`：启动时读取 `system_configs` 表里的 `transcode_encoder`（后台配置），回退到环境变量 `TRANSCODE_ENCODER`。
- 后台管理：新增"转码配置"页面（`/transcode-config`），归属"系统管理"菜单，可读/写编码器配置 + 显示本机 VAAPI 硬件状态。

> **体积 vs CPU 的取舍**：软编省 1.95x 体积，但吃 7 核 CPU 影响全机可用性——**在单机演示场景，实时可用性 > 存储成本**。行业上"点播用软编"的前提是专用服务器，本机不满足该前提，故采纳"默认硬编、可切换软编"的折中。

## 3. 决策：音频从 WAV 迁移到 MP3

### 3.1 背景

- 原 `ExtractAudio` 输出 **PCM WAV 16kHz 单声道**，音频合计 **52 MB**，占 MinIO 总存储 40%+。
- 计划弃用本地 Whisper，改用 **Cloudflare Workers AI**（`@cf/openai/whisper`）。

### 3.2 核实：Cloudflare Whisper 支持什么格式？

- **支持 MP3、MP4、WAV、WebM** 等多种格式（官方教程示例即用 `.mp3`）。
- **25 MB 单文件上限**：WAV 4 分钟约 40 MB 超限，而 MP3 128kbps 仅约 4 MB——转 MP3 不是妥协而是必需。
- 注意：社区有 4 分 28 秒 MP3 偶发报错反馈（Cloudflare 社区 #662925），需对最长视频实测。

### 3.3 代码改动

`transcode.go ExtractAudio()`：

```go
// 旧：PCM WAV
"-vn", "-acodec", "pcm_s16le", "-ar", "16000", "-ac", "1"

// 新：MP3（Cloudflare Whisper 兼容）
"-vn", "-acodec", "libmp3lame", "-b:a", "64k", "-ar", "44100", "-ac", "1"
```

`pipeline.go` 同步：key 从 `audio.wav` → `audio.mp3`，content-type `audio/wav` → `audio/mpeg`。

### 3.4 存储收益

| 指标 | 之前 (WAV) | 现在 (MP3) | 节省 |
|---|---|---|---|
| 音频合计 | 52 MB | **14 MB** | **73%** |
| MinIO 总占用 | 193 MB | **154 MB** | 20% |

最长视频 MP3 = 2.9 MB，远低于 Whisper 25 MB 上限。

## 4. MinIO 存储现状与优化方向（154 MB）

| 类型 | 大小 | 占比 |
|---|---|---|
| 转码分片 (720p HLS) | 71.8 MB | 48% |
| 源视频 (H.264 mp4) | 64.0 MB | 43% |
| 音频 (MP3) | 13.1 MB | 9% |

**结论**：转码分片 + 源视频占 91%，音频已不是大头。

### 潜在优化方向（未实施）

1. **补全 1080p / 480p 多档转码**：当前只有 720p 成功，建议未来按源分辨率决定档位集。
2. **分片 CRF 调优**：crf22 → 26 可再省 30-40% 分片体积。
3. **源视频与分片二选一**：源本就是 H.264，若接受直接播 MP4 可省掉 72 MB 分片。
