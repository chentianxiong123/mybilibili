# ADR-6：分布式部署与无状态水平拓展

> 状态：已决策（2026-08-30）
> 范围：fnos（主）+ laptop（备用）双节点 k3s 集群 + 手机边缘 worker

## 背景

现状：
- k3s 集群只有 1 台 fnos（192.168.31.225，amd64），同时担任 control-plane / etcd / worker
- 14 个 Deployment 全部 `replicas: 1`，无 HPA / 无 PDB / 无 nodeSelector
- 6 个 PVC 全部 `local-path` SC + RWO，单节点绑定（pg-data / minio-data / nats-data / studio-data / work-tmp / 默认命名空间两套）
- 业务服务互调走 k8s Service DNS（`search:9084` / `ai:9088` / `msg-danmaku:9086` / `bili:8091`），gRPC 客户端目前是 `grpc.NewClient` 无 LB 配置（默认 pick_first）
- 手机为 Android，**无法作为完整 k3s worker**（cgroup 受限 / iptables 受限 / Doze 冻结 / 网络切换）

需求：
1. 性能 / 容量拓展（高可用不是首要，但状态服务分布式顺带实现 HA）
2. 开发机（laptop, 192.168.31.204）作为 k3s 备用节点
3. 手机验证"无状态 Go 服务水平扩展"概念（不加入 k3s 控制面）

## 决策

### 1. 集群拓扑：fnos + laptop 双节点

| 节点 | 架构 | 角色 | 跑什么 |
|------|------|------|--------|
| fnos (192.168.31.225) | amd64 | k3s server + 主 | etcd / k3s control-plane / Traefik / PG primary / MinIO node-0 / NATS-0 / Redis / 业务副本各 1 |
| laptop (192.168.31.204) | amd64 | k3s agent + 备用 | PG replica / MinIO node-1 / NATS-1 / 业务副本各 1 / 保留 docker compose 本地开发 |

etcd 双节点：k3s 嵌入式 etcd 容忍 (N-1)/2 = 0 节点故障（2 节点 quorum=2），实际能容忍 0 节点宕机。**当且仅当两个节点都活着集群才健康**。这对"性能拓展"够用；要真正 HA 需加第 3 节点（后续）。

### 2. 状态服务分布式

#### 2.1 PostgreSQL：原生流复制

- 拆 `postgres` Deployment → `postgres-primary`（fnos）+ `postgres-replica`（laptop）
- 原生 streaming replication：primary 创建 `replication` slot，replica 启动 `pg_basebackup` + `standby.signal`
- 共享 `pg16-zhparser` 镜像，加 entrypoint 脚本判断 `PG_ROLE` env
- `nodeSelector` 锁节点：`postgres-primary` → fnos，`postgres-replica` → laptop
- 应用层**先保持单 DSN 都连 primary**（简化方案，零代码改动），replica 仅用于手动查询 / 报表
- 后续按需做读写分离：引入 `pkg/repository` 的 `MasterDB() / ReplicaDB()` 抽象

#### 2.2 MinIO：分布式 EC

- 改 `minio` Deployment → `StatefulSet`，`replicas: 2`
- 启动命令改 `minio server http://minio-0.minio-headless/data http://minio-1.minio-headless/data`
- EC:N = EC:1（2 节点最小容忍 1 节点故障）
- 每节点独立 PVC（`minio-data-0` + `minio-data-1`）
- 应用层 `MINIO_ENDPOINT=http://minio:9000` 不变（S3 SDK 用 path-style 即可）

#### 2.3 NATS JetStream：2 broker 集群

- 改 `nats` Deployment → `StatefulSet`，`replicas: 2`
- 加 `headless Service`（`nats-headless`）让 broker 互相发现
- 启动参数加 `-cluster=nats://0.0.0.0:6222 -routes=nats-route://nats-0.nats-headless:6222,nats-route://nats-1.nats-headless:6222`
- JetStream stream 配置 `replicas: 2`（自动跨节点复制）

### 3. 无状态服务 HPA + 多副本

10 个业务 Deployment（core / search / ai / msg-danmaku / live / studio / work / bili / web / admin）：
- `replicas: 2`（起步）
- `topologySpreadConstraints` 跨节点打散（`topologyKey: kubernetes.io/hostname`）
- `strategy: RollingUpdate`，`maxSurge: 1`、`maxUnavailable: 0`（滚动更新不中断）
- 加 `HorizontalPodAutoscaler`（CPU 60% 触发，min=2 max=8）
- 加 `PodDisruptionBudget`（`minAvailable: 1`）

gRPC 客户端加 `round_robin` 负载均衡：
```go
grpc.NewClient(addr,
    grpc.WithTransportCredentials(insecure.NewCredentials()),
    grpc.WithDefaultServiceConfig(`{"loadBalancingConfig":[{"round_robin":{}}]}`),
)
```
涉及：
- `mybilibili-go/core-service/internal/clients/search_client.go`
- `mybilibili-go/core-service/internal/clients/ai_client.go`
- `mybilibili-go/core-service/internal/clients/msg_danmaku_client.go`
- `mybilibili-go/work-service/cmd/work/main.go`（如有 gRPC/HTTP 客户端）

### 4. 镜像多架构构建

当前 Dockerfile 只构建 `linux/amd64`。手机 ARM64 需要 `linux/arm64` variant。

CI（`.github/workflows/ci.yml`）改 buildx 多架构：
- `platforms: linux/amd64,linux/arm64`
- manifest list（`latest` tag 兼容两种架构）
- 推 GHCR 时自动处理

### 5. 手机作为无状态 worker

**不加入 k3s**。手机通过以下方式跑无状态 Go 服务：

- Termux + proot-distro 装 Debian arm64 chroot
- chroot 内装 podman
- 从 GHCR 拉 ARM64 镜像：`podman pull ghcr.io/chentianxiong123/mybilibili-core:arm64-latest`
- 直接运行：`podman run --rm --network host -e PG_DSN=... ghcr.io/.../core:arm64-latest`
- 网络：手机与 fnos 同 LAN（192.168.31.x），直接可达
- Doze 防护：
  - `adb shell dumpsys deviceidle whitelist +com.termux`
  - Termux 前台 service + `termux-wake-lock`
  - `adb shell settings put global wifi_sleep_policy 2`（Wi-Fi 永远不睡）
  - 开发者选项 → 不锁定屏幕
- 验证 service：选 `core`（Go 静态二进制，ARM64 完美支持，最稳）

### 6. 开发机的双重身份

- k3s agent 常驻
- docker compose 保留，**只跑基础设施**（pg16 / minio / redis / nats），**不跑业务服务**
- 业务服务全部走 k3s
- 端口冲突：compose 让出 80/443 给 k3s Traefik，compose 改用 9080/9443 高位端口
- 业务开发走 `kubectl logs -f` / `kubectl exec` 调试

## 落地步骤

### 阶段 0：基线快照
- 备份 deploy/k3s/ 目录
- 记录所有现有 PVC
- 记录 fnos k3s node-token

### 阶段 1：开发机接 k3s agent（双节点 etcd）
- fnos 取 token：`cat /var/lib/rancher/k3s/server/node-token`
- laptop 装 agent：`curl -sfL https://get.k3s.io | INSTALL_K3S_EXEC="agent --server https://192.168.31.225:6443 --token <TOKEN> --node-name laptop" sh -`
- 验证：`kubectl get nodes` 看到 2 个 Ready

### 阶段 2：状态服务分布式
- 2.1 PostgreSQL 主从
- 2.2 NATS 集群
- 2.3 MinIO 分布式

### 阶段 3：无状态服务多副本
- 改 backend.yaml / frontend.yaml
- 加 HPA + PDB
- gRPC 客户端 round_robin

### 阶段 4：手机 ARM64 验证
- CI buildx 多架构
- 手机 Termux + proot-distro + podman
- 跑 core 镜像
- 防 Doze 配置

### 阶段 5：验收
- fnos 故障演练（业务 pod 全部 delete，laptop 副本接管）
- 手机断网演练（手机掉线不影响集群）
- 性能基线（ab / hey 压测）

## 风险与备选

| 风险 | 备选 |
|------|------|
| etcd 2 节点 quorum 边界（容忍 0 节点故障） | 加第 3 节点（ARM64 盒子）升 3 节点集群，quorum=2 容忍 1 节点故障 |
| PG 同步延迟导致从库读旧数据 | 关键读走 primary（库存 / 计数），非关键读走 replica |
| 手机 Doze 仍然杀进程 | 改"心跳上报"模型：手机主动每 5 秒 ping，30 秒没 ping 视为离线 |
| 镜像 ARM64 编译出 bug | 先用 scratch base 重写 multi-stage，不依赖 glibc |
| MinIO 2 节点 EC:1 不能容忍同节点多盘故障 | 加第 3/4 节点升 EC:2 |
| 开发机 docker compose 与 k3s agent 端口冲突 | compose 让出 80/443，业务服务全部走 k3s |

## 排除项

- 前端 SSR（Nuxt）在手机上跑 — 浏览器 / Node 兼容性差，没意义
- 手机集群 gossip（手机之间 P2P 互联）— 不是 k3s 控制面，复杂度爆炸
- 真的让手机进 k3s（按 Android 内核限制，几乎不可能）
- 公网 / 异地多集群 — 单 LAN 内
- HPA V2 自定义指标（QPS / 延迟）— 只用 CPU 默认
- 滚动更新灰度（canary / blue-green）— 单 LAN 暂时不需要

## 结论

fnos + laptop 双节点 k3s 集群 + 状态服务分布式 + 无状态服务 HPA + 手机 ARM64 边缘 worker，实现性能 / 容量水平拓展，同时附带基础 HA。手机不加入 k3s 控制面，通过独立运行无状态服务容器验证"水平扩展"概念。
