# WebSocket vs HTTP CRUD vs SSE：连接模型分析与选型

## 1. 为什么纠结这个

重构时最容易踩的坑：**把单向场景做成 WebSocket，把长连接场景做成轮询**。两者都是资源浪费，只是方向不同。

- 单向场景用 WS → 每连接 20KB 常驻，只为推一个通知
- 实时场景用轮询 → 每 3 秒 1 次请求，只为等一条弹幕

先想清楚三种技术的本质差异，再按场景选，而不是"实时就上 WS"。

---

## 2. 三种技术全景对比

| 维度 | HTTP CRUD | SSE | WebSocket |
|------|-----------|-----|-----------|
| 底层协议 | HTTP/1.1、HTTP/2 | HTTP（长响应） | TCP 独立帧协议 |
| 连接模型 | 短连接，请求-响应，用完即断 | 长连接，单向推送 | 长连接，全双工 |
| 数据方向 | 双向（请求/响应） | **服务端 → 客户端** | 双向，任意时刻 |
| 连接数 | 无状态，用完即释放 | 每客户端 1 条，常驻 | 每客户端 1 条，常驻 |
| 单连接资源 | 极低（请求后释放） | 低（HTTP 层复用） | 高（goroutine + 双 buffer + 心跳） |
| 空闲开销 | 无 | 心跳开销（HTTP/2 可省） | 心跳 + 帧解析 + 缓冲 |
| 断线重连 | 天然（新请求） | 内建（EventSource 自动重连 + Last-Event-ID） | 需自建（心跳检测 + 重连逻辑） |
| 客户端支持 | 全部 | 全部浏览器 + fetch 流式读取 | 浏览器/移动端原生支持，某些网络代理会拦 |
| 代理友好度 | 最友好 | 友好（标准 HTTP 响应） | 一般（需要代理识别 Upgrade，超时配置） |
| 消息格式 | JSON/任意 | text/event-stream，文本为主 | 文本 + 二进制任意 |
| 服务端实现 | 最简 | 简单（一条流式响应） | 复杂（连接管理、心跳、扇出） |
| 背压处理 | 无需 | 需控制写速率 | 需处理慢消费者 |
| 适用规模 | 无限（无状态） | 10 万级连接单机 | 10 万级连接单机 |

**一句话总结：**
- **HTTP CRUD**：有事才说话，说完就散
- **SSE**：单向播报，像收音机
- **WebSocket**：双向对讲，像电话

## 3. 连接资源深度分析

### 3.1 单连接内存构成（Go 服务端）

| 组成部分 | 默认大小 | 说明 |
|----------|---------|------|
| goroutine 栈 | ~4KB（可增长） | 每连接一个 goroutine |
| 读缓冲 | ~4KB | gorilla/websocket 默认 |
| 写缓冲 | ~4KB | 同上 |
| 连接结构 | ~1KB | 房间、用户、订阅元数据 |
| 应用层 | ~8KB | 在线列表、房间广播 channel、心跳计时器 |
| **单连接合计** | **~20KB** | 生产环境按此估算 |

### 3.2 量化到 MyBilibili 规模

| 场景 | 连接数 | 内存占用 | 盒子 1GB 占比 |
|------|--------|---------|--------------|
| 1000 注册用户，峰值在线 200 | 200 | ~4MB | 0.4% |
| 峰值在线 2000（10 倍膨胀） | 2000 | ~40MB | 4% |
| 峰值在线 10000（广告级） | 10000 | ~200MB | 20% |

**结论：1000 用户规模，WS 内存根本不是问题。** 真正要防的是"每人 3 条连接"的滥用：
- 弹幕 1 条 + 消息 1 条 + 在线状态 1 条 = 3 条/人
- 3 倍连接 = 3 倍内存 + 3 倍 fd + 3 倍心跳

### 3.3 非内存资源

| 资源 | WS | SSE | HTTP CRUD | 说明 |
|------|-----|-----|-----------|------|
| 文件描述符 fd | 1/连接 | 1/连接 | 瞬时 | WS/SSE 都要调 `ulimit -n`（默认 1024 不够） |
| 心跳流量 | 每 30-60s ping/pong | HTTP/2 层心跳 | 无 | 1000 连接 × 每 30s ≈ 33 条/s，可忽略 |
| CPU | 帧解析 + 扇出 | 写响应流 | 序列化 + 解析 | WS 高，SSE 中，CRUD 中 |
| 带宽 | 小消息即可 | 纯文本冗余大 | 每请求头开销 | WS < SSE < CRUD |
| 连接状态保持 | 需服务端存储 | 无需（HTTP 无状态） | 无 | WS 有状态，扩容要迁移 |

### 3.4 SSE 为什么比 WS 省

| 对比项 | WS | SSE |
|--------|-----|-----|
| 握手 | Upgrade 升级，服务端要支持 | 普通 HTTP，任意代理直接转发 |
| 方向 | 双向（维护双向通道） | 单向（只维护下行流） |
| 重连 | 业务自建 | 浏览器 EventSource 内建 |
| 实现复杂度 | 连接管理 + 心跳 + 扇出 | 一条流式响应 + 定时写 |
| 资源系数 | **1.0** | **~0.2** |

**经验值：同样规模的单向推送，SSE 资源消耗约为 WS 的 1/5。**

## 4. 适用场景对照表

| 业务场景 | 数据方向 | 实时性要求 | 正确选择 |
|----------|---------|-----------|---------|
| 视频列表/详情 | 请求-响应 | 秒级 | **HTTP CRUD** |
| 点赞/收藏/关注 | 请求-响应 | 秒级 | **HTTP CRUD** |
| 消息中心列表 | 请求-响应 | 秒级 | **HTTP CRUD** |
| 评论加载 | 请求-响应 | 秒级 | **HTTP CRUD** |
| 新消息提醒 | 单向推送 | 秒级 | **SSE** |
| 评论区实时更新 | 单向推送 | 秒级 | **SSE** |
| 动态/关注流推送 | 单向推送 | 秒级 | **SSE** |
| 转码进度 | 单向推送 | 秒级 | **SSE** |
| 弹幕发送 + 接收 | 双向 | 百毫秒级 | **WebSocket** |
| 直播信令（连麦/会议） | 双向 | 百毫秒级 | **WebSocket** |
| 在线状态/心跳 | 双向 | 秒级 | **WebSocket**（或省略） |
| 直播媒体流 | 单向大流量 | 秒级 | **HLS/FLV（纯 HTTP）** |
| 文件上传下载 | 请求-响应 | 秒级 | **HTTP CRUD（分片）** |

**选型铁律：先看方向，再看实时性。**
1. 不是双向 → 永远不考虑 WS
2. 双向 + 毫秒级 → WS
3. 单向 + 需要服务器主动推 → SSE
4. 单向 + 客户端主动拉 → HTTP CRUD

## 5. 三个常见误区

### 误区 1：实时 = WebSocket

真相：90% 的"实时"是单向通知。评论区、通知、动态流都是"别人发了我看到"，SSE 完全胜任，资源省 5 倍。

### 误区 2：SSE 浏览器不支持

真相：所有现代浏览器（含移动端）原生支持 `EventSource`。只有极老 IE 不支持，可降级为轮询。

### 误区 3：WS 连接断了要自己重连

真相：SSE 的 `EventSource` 断线自动重连，还带 `Last-Event-ID` 续传；WS 的断线重连要业务自己写。**能把复杂度交给浏览器的，别自己扛。**

## 6. MyBilibili 落地决策

### 6.1 最终连接分级

```
┌──────────────────────────────────────────────────────────┐
│                    客户端（Web/移动端）                     │
│   HTTP CRUD          SSE                 WebSocket         │
│  /api/v1/...     /sse/notify          /ws/danmaku         │
│  /api/v1/...     /sse/comment         /ws/live            │
│  /api/v1/...     /sse/progress        (直播信令)           │
└──────┬──────────────────┬──────────────────┬─────────────┘
       │                  │                  │
       ▼                  ▼                  ▼
┌──────────────────────────────────────────────────────────┐
│                        Traefik 网关                        │
│   HTTP 路由             流式响应             Upgrade 代理     │
└──────┬──────────────────┬──────────────────┬─────────────┘
       │                  │                  │
       ▼                  ▼                  ▼
   core 胖单体        core 胖单体          core 胖单体
   (CRUD handler)   (SSE handler)        (WS hub + NATS)
```

### 6.2 各业务场景选型

| 功能 | 选型 | 理由 |
|------|------|------|
| 弹幕 | **WebSocket** | 发送 + 接收都实时，双向 |
| 直播信令（连麦/会议） | **WebSocket** | 双向控制流 |
| 直播媒体流 | **HLS（HTTP）** | 单向下行，标准代理直接支持 |
| 消息通知 | **SSE** | 单向推送，浏览器自动重连 |
| 评论区更新 | **SSE** | 单向展示 |
| 动态/关注流 | **SSE** | 单向推送 |
| 转码/导出进度 | **SSE** | 单向进度流 |
| 全部 CRUD | **HTTP（对内 gRPC）** | 请求-响应 |

### 6.3 弹幕 WS 内部设计

```
发弹幕:  POST /api/v1/danmaku          (HTTP CRUD，落库路径)
            ↓
       验证 + 写 Redis 缓冲          (写路径，不阻塞)
            ↓
       广播到房间: channel 扇出        (单实例)
                 NATS pub/sub        (多实例，部署副本时)
            ↓
       WS /ws/danmaku 推给房间内所有人
```

- 广播单实例用 channel 扇出，多实例用 NATS pub/sub
- 高频小弹幕批量合并后推送，避免每帧一次写
- 弹幕用 protobuf 编码，比 JSON 省 ~60% 带宽

### 6.4 连接治理清单

| 策略 | 做法 | 目的 |
|------|------|------|
| 每用户单连接 | 重复登录踢掉旧连接 | 防连接数翻倍 |
| 空闲超时 | 60s 无消息关闭，前端自动重连 | 回收僵尸连接 |
| 单 IP 限连接数 | 如 5 条/IP | 防刷 |
| fd 上限 | `ulimit -n 65535` | 支撑长连接 |
| 二进制协议 | WS 消息用 protobuf | 省带宽省解析 |
| 慢消费者保护 | 写超时断开 + 队列有界 | 防一慢拖全队 |

## 7. 与网关（Traefik）的配合

| 类型 | 路由规则 | 网关配置要点 |
|------|---------|-------------|
| HTTP CRUD | `/api/v1/*` | 普通 HTTP 路由，负载均衡、限流、JWT |
| SSE | `/sse/*` | 同 HTTP，但响应头 `Cache-Control: no-cache`，**禁止代理缓冲**，读超时调大 |
| WebSocket | `/ws/*` | 需网关支持 Upgrade 转发，连接空闲超时调大，开启 `readTimeout=0` |

**关键点：**
- Traefik 对 SSE 是标准 HTTP 响应，天然支持，无需特殊插件
- Traefik 对 WS 需要配置 `readTimeout`/`writeTimeout` 为 0，防止中间层切断长连接
- SSE/WS 都是长连接，网关健康检查、滚动发布时要做**优雅下线**（先停新流量，等存量连接自然结束）

## 8. 扩容与故障考虑

| 场景 | HTTP CRUD | SSE | WebSocket |
|------|-----------|-----|-----------|
| 水平扩容 | 随便加实例，无状态 | 加实例即可，连接无需迁移 | **连接有状态**，需粘性路由或网关重连 |
| 实例重启 | 无感知 | 客户端自动重连（EventSource） | 客户端需自建重连 |
| 故障半径 | 单请求 | 单连接 | 单连接 + 房间广播可能受影响 |
| 规模上限 | 无 | 单机 10 万级 | 单机 10 万级，但连接管理复杂 |

**长连接的唯一副作用是"有状态"。** 解决手段：
1. **粘性路由**：Traefik 按用户 cookie/IP 固定到同一实例（保 WS 不断）
2. **优雅下线**：实例退出前给前端发"reconnect"事件，让客户端主动重连到健康实例
3. **连接无状态化设计**：WS 连接内不存业务状态，状态全在 Redis/PG（断线重连后能恢复上下文）

---

## 9. 结论

1. **HTTP CRUD 是默认**：90% 功能是请求-响应，别为"实时"硬上长连接
2. **单向推送用 SSE**：通知、评论区、进度，省资源 5 倍，浏览器自动重连
3. **WebSocket 只给真双向**：弹幕、直播信令。1000 用户规模下 200 连接 ~4MB，不是瓶颈
4. **直播媒体流用 HLS**：那是 HTTP 的活，不是 WS 的活
5. **连接治理是必修课**：每用户单连接、空闲超时、fd 上限、二进制协议
6. **长连接要配合网关**：SSE 禁缓冲、WS 关读写超时、优雅下线

**选型一句话：双向且毫秒级 → WS；单向需推送 → SSE；其余 → HTTP CRUD。**
