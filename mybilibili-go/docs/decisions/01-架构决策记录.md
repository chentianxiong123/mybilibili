# 架构决策记录

## ADR-1：Go 单体 vs Java 8 微服务

### 背景
旧版 `mybilibili-cloud` 为 Java Spring Cloud 微服务架构，共计 12 服务 → 合并为 8 服务。

### 决策
采用 Go 单体架构，所有业务逻辑在单个进程中运行。

### 依据
| 维度 | Java 8 微服务 | Go 单体 | 倍数 |
|------|---------------|---------|------|
| 单服务基础内存 | 256-512MB（JVM + 框架） | 10-20MB（静态二进制） | 15-25x |
| 8 服务合计 | 2-4GB | 80-160MB（单体） | 25x |
| 启动时间 | 30-60s | <100ms | 300-600x |
| 镜像大小 | ~200MB（JDK + Spring） | ~20MB | 10x |
| CPU 空闲开销 | 5-10%（GC + 框架循环） | <0.1%（epoll 等待） | 50-100x |
| 编译产物 | 21MB 单体 | 21MB 单体 | — |
| 源码行数 | — | 19K 行 / 99 文件 | — |

### 结论
Go 单体以 1/15 的内存、1/10 的机器成本做到 Java 8 服务 70%+ 功能对齐。

## ADR-2：PG 一库三用

### 背景
旧版使用 MySQL + MongoDB + Elasticsearch 三套存储。

### 决策
PostgreSQL 同时承担关系数据库、文档存储、搜索引擎三个角色。

### 实现
| 角色 | 替代方案 | PG 特性 |
|------|---------|---------|
| 关系数据 | MySQL | 原生 |
| 文档存储 | MongoDB | JSONB + GIN 索引 |
| 全文搜索 | Elasticsearch | tsvector + pg_trgm |
| 向量检索 | 无 | pgvector（HNSW） |

### 结论
单项目规模下 PG 完全够用，部署复杂度从 4 个中间件降为 1 个。

## ADR-3：AI 侧车策略

### 背景
AI 摘要/审核/客服需要 LLM 推理，但 CPU 密集任务不宜在主进程内执行。

### 决策
AI 逻辑作为独立侧车进程运行，Go 主进程通过 HTTP 或 gRPC 调用。

### 架构
```
Go 单体 (21MB)  ──HTTP──▶  AI 侧车
 业务 CRUD                      LLM 调用
 状态机/事件                    内容审核
 PG 三合一                      Whisper 推理
 FFmpeg 编排                   摘要生成
```

### 侧车语言选择
废除 Python 方案。侧车可以用：
- Go 自身（编译为独立二进制，与主进程同语言栈）
- Rust/C++（如需要极致推理性能，调 llama.cpp）
- 核心原则：不做 Spring Native，不做 Python

### 结论
AI 先放一放，等 LLM 接入条件成熟时再按侧车模式接入。当前 AI 域代码结构完整，缺的是后端模型，不是架构。

## ADR-4：外部进程编排

### 背景
视频转码、字幕生成等 CPU 密集型任务。

### 决策
通过 `os/exec` 调外部进程，而非在进程内计算。

### 依据
| 方案 | 延迟 | 隔离性 | 开发成本 |
|------|------|--------|---------|
| 调外部进程 | 10-100μs | ✅ 完全隔离 | 低 |
| 进程内计算 | 0 | ❌ 崩溃拖垮主进程 | 高 |
| 微服务 RPC | 1-10ms | ✅ 隔离 | 极高 |

### 结论
ffmpeg / whisper 等工具以子进程方式运行，开销极小且天然隔离。

## ADR-5：业务日志（login/audit/ai_usage）存储位置

### 背景
- 实现了 admin/user login-logs 和 audit 功能后，数据直接 INSERT 到 PG 表（login_logs / audit_logs / ai_usage_logs）。
- 用户问：“这种数据适合写哪里？”（架构文档明确日志用 Loki）。
- 同时清空了所有日志表。

### 决策
**业务事件日志继续使用 PostgreSQL 主库 + 时间分区（RANGE by month） + 保留策略。**

Loki 仅用于应用运行日志（observability / debug / error 聚合）。

### 依据
- **性质不同**：
  - login_logs/audit_logs/ai_usage_logs：结构化、可按用户/模块过滤、分页、关联查询、UI 展示（个人中心/管理后台）。需要 ACID、索引、join。
  - 应用日志：非结构化或半结构化文本，用于排查、监控、告警。Loki 按标签查询。
- **架构一致性**：08-technology-selection 里的 Loki 是“可观测性”组件，和业务数据表不冲突。
- **硬件约束**：PG 部署在老电脑（HDD），盒子不直接持主库；分区 + 定期 DROP 旧分区可控写入和空间。
- **02-logging-strategy** 讨论的是文件/ringbuffer 日志，不是业务事件表。

### 实现
- 新建 `sql/025_partition_log_tables.sql`（重建为分区表 + 示例月分区 + 注释）。
- 更新 `999_go_tables.sql` 中 login_logs / ai_usage_logs 为分区形式（audit 仍主要在 009_admin.sql）。
- 保留策略：login 6个月、audit 12个月、ai 3个月（通过 scheduler 或外部 cron DROP 分区）。
- 代码写入点不变（仍直接 INSERT），查询 SQL 自动受益于分区裁剪。

### 结论
- 业务可查询的历史记录 → PG 分区表（已实施）。
- 运行时诊断日志 → 后续结构化 slog + Loki（待 infra 补 Loki）。
- NATS 可作为可选的“审计事件”异步通道（P2，不急）。
