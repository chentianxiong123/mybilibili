# 终极架构定稿：混合微服务

## 一、核心结论：SQLite 到底有没有用

在正确的位置上，SQLite 是核武器；在错误的位置上，它是鸡肋。

| 场景 | SQLite 表现 | 结论 |
|------|------------|------|
| 当主数据库（替代 MySQL） | 写锁瓶颈，无法承受高并发 | ❌ 没用 |
| 当分布式集群（Raft 共识） | 嵌入式设备太耗资源，服务器端不如直接 MySQL | ⚠️ 勉强 |
| **当本地 L1 缓存（最外层）** | **mmap 零拷贝，比 Redis 快 50 倍，省掉网络开销** | **✅ 封神** |
| **当胖二进制只读副本** | **弹性伸缩利器，挂载即用，秒级扩容** | **✅ 王牌** |

## 二、最终选型：混合微服务架构

```
┌─────────────────────────────────────────────────────────┐
│                    前端/网关层                          │
└──────────────┬──────────────────┬──────────────────────┘
               │                  │
          读多写少流量          强一致事务流量
               │                  │
               ▼                  ▼
    ┌──────────────────┐  ┌──────────────────┐
    │  Go 非关键链路    │  │ Java 关键链路    │
    │ (胖二进制+SQLite) │  │ (传统微服务)      │
    │  - 视频详情页     │  │  - 支付/订单      │
    │  - 推荐/热度      │  │  - B币/硬币      │
    │  - 评论展示       │  │  - 库存扣减      │
    │  - 配置缓存       │  │  - 用户资产      │
    └────────┬─────────┘  └────────┬─────────┘
             │                     │
    读：本地SQLite       写：直接MySQL事务
    (mmap零拷贝)         (强ACID保证)
             │                     │
             └──────────┬──────────┘
                        ▼
               ┌──────────────────┐
               │  消息队列(NATS)  │ ← 异步削峰填谷
               └────────┬─────────┘
                        ▼
               ┌──────────────────┐
               │  MySQL(归档层)   │ ← 唯一真相源，压力降低 90%
               └──────────────────┘
```

## 三、五大黄金法则

### 1. 读写彻底分离

读走本地 SQLite（L1 缓存），写走队列异步归仓。强一致链路直接绕过这套，直写 MySQL。

### 2. 胖二进制 = 无状态

SQLite 文件只是 OSS 快照的只读副本，Pod 销毁时直接删除。扩容时通过 Init Container 预加载快照，秒级启动，随意弹性伸缩。

### 3. 分层缓存（L1 → L2 → L3）

| 层级 | 组件 | 延迟 | 职责 |
|------|------|------|------|
| L1（最外层） | 本地 SQLite（mmap） | ~0.01ms | 扛热点读 |
| L2（中间层） | Redis | ~0.5ms | 分布式锁、全局计数器 |
| L3（归档层） | MySQL | ~5ms | 绝对真相源 |

### 4. 崩溃分级保障

| 链路 | 策略 |
|------|------|
| 强一致（支付/资产） | 直接走 Java + MySQL 事务，不用 SQLite |
| 核心互动（评论/投币） | 先写本地 SQLite(WAL) 再返回成功，后台异步同步 |
| 纯统计（播放量） | 纯内存累加，丢了不可惜，资源零消耗 |

### 5. 关键/非关键链路分离

| 链路 | 语言 | 职责 |
|------|------|------|
| 关键链路（0.01% 流量） | Java | 处理强一致业务，启动慢但稳如泰山 |
| 非关键链路（99.99% 流量） | Go | 处理读流量，15MB 二进制，随意扩缩容 |

## 四、为什么这是最优解

| 维度 | 传统微服务 | 混合架构 |
|------|----------|---------|
| 启动内存 | 200MB+（挂载一堆 Agent） | 80~150MB（纯业务） |
| 读延迟 | ~5ms（查 Redis/MySQL） | ~0.01ms（本地 mmap） |
| 扩容速度 | 30~60 秒（等待连接池） | <2 秒（挂载快照即用） |
| 资源利用率 | 低（CPU 闲置，内存浪费） | 极高（榨干每一滴性能） |
| 依赖数量 | Redis+MQ+MySQL+... | 只有 OSS+MySQL+MQ（Redis 可降级） |
| 弹性能力 | 受限于中心连接数 | 无限扩展（不依赖中心） |
| 故障半径 | 中心故障引发雪崩 | 单实例故障只影响 2% 请求 |

## 五、最终决策路径

### ✅ 采纳方案

- Java 服务处理支付、订单、资产等强一致链路
- Go 胖二进制服务处理视频详情、推荐、热度等读密集型链路
- SQLite 作为 Go 服务的 L1 本地缓存，mmap 零拷贝读取
- 写入全部走 MQ 异步归仓，不阻塞业务
- OSS 定时生成全量快照，扩容时 Init Container 预加载
- Redis 降级为分布式锁和少量全局计数器

### ❌ 放弃方案

- SQLite 作为主数据库替代 MySQL
- SQLite 作为分布式共识存储（rqlite/Dqlite）
- `:memory:` 内存数据库（重启丢失，扩容慢）

## 六、落地行动清单

| 序号 | 行动项 | 优先级 |
|------|--------|--------|
| 1 | Go 胖二进制：实现 SQLite mmap 本地缓存 | P0 |
| 2 | 抽象层：Cache/Repository 接口，支持切换本地/远程实现 | P0 |
| 3 | OSS 快照：定时任务生成全量 SQLite.db，上传 OSS | P0 |
| 4 | Init Container：Pod 启动时拉取快照挂载到 `/dev/shm` | P1 |
| 5 | 增量同步：Go 服务监听 MQ 增量消息，更新本地 SQLite | P1 |
| 6 | Java 服务保留：处理支付/订单等强一致链路 | P1 |
| 7 | 监控告警：SQLite 文件大小、命中率、同步延迟 | P2 |

## 七、架构演进路线

从"大单体"到"海量微服务"是技术膨胀，从"海量微服务"回到"模块化单体 + 混合部署"才是技术精华。

这套架构既保留了微服务的逻辑隔离优势，又拿回了单体的极致性能；既能用 Java 守住资金安全，又能用 Go 轻骑兵横扫海量流量。

这已经不是"能不能用"的问题，而是"谁先用谁先起飞"的问题。
