# 前后端一体化二进制包：源码分离，部署合一

## 1. 历史脉络：从杂糅到分离再到合一

```
JSP/PHP（源码杂糅）
    │  HTML + SQL + Java 写在一个文件里
    │  改个样式要改 .java，改个SQL要改 .jsp
    ▼
前后端分离（源码分离，部署分离）
    │  Vue 独立仓库 / Go 独立仓库
    │  前端 Nginx → 后端 API → 两个进程
    ▼
二进制内嵌（源码分离，部署合一）
    │  Vue 源码独立 / Go 源码独立
    │  go:embed → 一个二进制搞定
```

**JSP 的问题不是"前后端在一起"，而是"代码杂糅"**——展示逻辑和业务逻辑、前端代码和后端代码物理上混在一个文件里，改一行动态牵全身。

**二进制内嵌刚好相反**：源码层是严格分离的（`web/` 独立目录，Vite 独立构建），但部署层合为一个文件。分离的是**关注点**，合一的是**交付物**。

---

## 2. 关键区别：源码分离 vs 部署合一

| 比较 | JSP 杂糅 | 前后端分离（Nginx+API） | 二进制内嵌 |
|------|---------|----------------------|-----------|
| 源码组织 | HTML+Java 混写 | 独立仓库/独立目录 | 独立目录，`web/` vs `internal/` |
| 开发体验 | 改完重启服务器 | 前端热更新，后端独立 | 前端热更新，后端独立（同左） |
| 构建 | 直接部署源码 | 前端 build → Nginx，后端 build → 进程 | 前端 build → go:embed → 编译 |
| 部署 | 1 个 war 包 | 2 个组件（Nginx + 进程） | **1 个二进制** |
| 扩容 | 加机器 | 前端 CDN + 后端加实例 | 加实例（前端自带） |
| 前端更新 | 无独立概念 | 独立部署，不重启后端 | 需重新编译（但 10KB 构建秒级） |

**核心：JSP 是"分不开"，二进制内嵌是"不想分"——有能力分，但选择合。**

---

## 3. 二进制内嵌的优势

### 3.1 部署极简

```bash
# 传统：需要 3 步
npm run build          # 前端构建
scp dist/ user@host:/var/www/   # 上传前端
scp server user@host:/opt/      # 上传后端
systemctl restart nginx server  # 重启两个服务

# 二进制内嵌：1 步
GOOS=linux GOARCH=arm64 go build -o mylib ./cmd/mylib
scp mylib user@host:/opt/mylib
systemctl restart mylib
```

**一个 scp，一个 restart，零依赖。** 对于盒子部署（没有 Nginx、没有 CDN、没有 CI/CD），这就是巨大优势。

### 3.2 版本对齐

前后端永远是一起发布的，不会出现"前端 V2.1 调后端 V2.0 的接口已废弃"的错配问题。**一个二进制 = 一个版本 = 一个部署单元。**

### 3.3 资源利用率

- 传统：Nginx 占 ~30MB 内存（静态文件代理），后端占 ~15MB，合计 ~45MB
- 内嵌：Go 的 `http.FileServer` 内嵌，零额外内存，**合计 ~15MB**

对于 1GB 盒子，省 30MB 就是省 3% 的总内存。

### 3.4 无状态扩容

传统扩容时，新实例要配 Nginx 或配 CDN。内嵌方案：**新实例启动就是完整服务**，自带前端，Traefik 只管 gRPC 路由，静态文件由业务进程自己处理。

## 4. 什么时候不该内嵌

| 场景 | 原因 | 对策 |
|------|------|------|
| 前端频繁更新（每天几次） | 每次前端改版要重新编译 Go | 切 external 模式，CDN 分发 |
| 前端体积大（> 1MB） | 内嵌膨胀二进制，编译慢 | 优化体积或切 external |
| 前后端不同团队开发 | 发布节奏不同，耦合 | 应该分离部署 |
| 需要 CDN 边缘缓存 | 内嵌走不了 CDN | 切 external 模式 |

**mybilibili 场景判断**：
- 前端优化后 ~10KB → 体积不是问题
- 个人项目，一人开发 → 无团队协作问题
- 盒子部署，无 CDN → 内嵌是最优解
- 配置开关保底，未来规模大了切 external 即可

---

## 5. 对比总结

| 维度 | JSP 杂糅 | Nginx + 前后端分离 | 二进制内嵌（推荐） |
|------|---------|-------------------|-----------------|
| 源码组织 | ❌ 混在一起 | ✅ 严格分离 | ✅ 严格分离 |
| 部署复杂度 | 中（war 包） | 高（2 个组件） | **低（1 个文件）** |
| 版本对齐 | 自动 | 需手动 | **自动** |
| 盒子友好 | 不友好（JVM 重） | 一般（Nginx 额外开销） | **最友好** |
| 扩容成本 | 中 | 高（前端也要配） | **低** |
| 前端独立更新 | ❌ | ✅ | ⚠️ 需重新编译 |

## 6. 结论

**二进制内嵌不是开倒车回到 JSP 时代，而是站在"源码已经分离"的基础上，选择"部署时合起来"**。源码分离保证可维护性，部署合一保证运维简洁性——两者不矛盾，两全其美。

用一句话概括：**源码是模块的，部署是原子的。** 这是现代云原生单体（modular monolith）的标配实践。
