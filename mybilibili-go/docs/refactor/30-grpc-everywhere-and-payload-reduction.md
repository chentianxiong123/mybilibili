# 全链路 gRPC：传输形态统一与减量策略

## 1. 为什么要纠结这个

目前的胖单体是 **HTTP(:8080) + gRPC(:9090) 双通道并存**：

- 内部模块调用（user/manuscript/comment/interaction）走 gRPC，其余走 HTTP JSON
- 对外响应几乎全是 JSON，存在大量冗余：字段名重复传输、冒号引号、类型全部字符串化、返回了根本没人用的字段

传输量的浪费是真实的，举一个例子：

```json
// 一条视频列表项，JSON 传输 240 字节
{"id":1001,"title":"直播回放","cover_url":"/cover/1001.jpg","view_count":1024,"like_count":88}
// 同样的内容，Protobuf 传输约 60 字节，体积差 4 倍
```

单条是小事，**10 万 QPS 的列表接口就是每天几 TB 的带宽差**。

本篇要回答一个统一的问题：**能不能让内部所有通道都走 gRPC？JSON 怎么办？传输量怎么减？未来的衍生产品如何同样受益？**

---

## 2. 统一原则：内部通道一律 gRPC

### 2.1 分层视角

| 层级 | 首选 | 原因 |
|------|------|------|
| 服务内部 模块间调用  | gRPC | 省握手、省体积、强契约 |
| 服务间 微服务调用  | gRPC | 同上，且天然服务发现友好 |
| 浏览器/App 直连（Web API） | HTTP JSON | 浏览器不支持 gRPC |
| 浏览器实时推送 | SSE / WebSocket | 见文档 20，不强行换协议 |
| 二进制文件/媒体 | 对象存储直连 | 不走应用协议，CDN 才是正道 |
| 运营后台（内部工具） | gRPC-Web / JSON | 按团队工具链定 |

**核心结论：协议选择由“谁在消费”决定，而不是“哪个更快”单点决定。**
凡是服务端到服务端的通道，统一用 gRPC；凡是浏览器/第三方直连的边界，保留 HTTP JSON。

### 2.2 一个容易踩的坑

不要因为迷信 gRPC 而把浏览器接口也包一层 gRPC-Web。这不是减量，是把复杂度转嫁到前端工程。**gRPC 的目标是内网服务对服务的低延迟高吞吐，不是取代 W3C 的 HTTP。**

## 3. 减量三板斧

### 3.1 Protobuf：-60% ~ -90% 体积

| 维度 | JSON | Protobuf |
|------|------|----------|
| 编码 | UTF-8 文本 | 变长二进制（Varint） |
| 字段名 | 每次都传 | 只在 .proto 定义一次（字段号=1字节） |
| 数字 | "1024" → 5字节 | 1024 → 2字节 |
| 空值 | 仍占 null/字段或引号 | 默认值直接省略 |
| 编解码成本 | 高（反射+字符串解析） | 低（定长偏移量 + 内联） |

### 3.2 裁剪：只传输消费方需要的字段

比编码更狠的减量是**根本不生成你不用的字段**：

- 列表接口只返回 `id/title/cover/summary`，详情才返回全量
- 用 `FieldMask`（gRPC 请求里声明需要的字段子集），服务端按需填充
- 数组分页/游标，绝不一次拖全表
- 聚合指标（view_count/like_count）与正文分离，减少高频刷新时的重传

### 3.3 HTTP/2 传输红利

gRPC 跑在 HTTP/2 上，白送的三个能力：

| 能力 | 效果 |
|------|------|
| 多路复用 | 单连接并发 100+ 流，无应用层队头阻塞 |
| 头部压缩（HPACK） | 每次请求的元数据接近 0 开销 |
| 长连接复用 | 省掉每次 TLS 握手 + RTT |

## 4. JSON 往哪去

**JSON 不会从这个世界消失，它退化为"边界协议"。**

| 用途 | 是否保留 JSON | 理由 |
|------|:---:|------|
| 对外 Web/App API | ✅ 保留 | 浏览器/生态强制 |
| 内部服务调用 | ❌ 改 proto | 减量 + 强契约 |
| 配置（.json/.jsonc） | ✅ 保留 | 人读的、低频、体积无所谓 |
| 日志结构化输出 | ✅ 保留 | 生态（ELK/Tempo 等）兼容 |
| 缓存序列化 | ⚠️ 视情况 | 大对象改 proto，小对象保持 JSON |
| 消息队列事件载荷 | ⚠️ 视情况 | 跨语言消费者多就留 JSON，纯内部改 proto |
| AI 模型输入/输出 | ✅ 保留 | 模型生态绑死 JSON |

**一句话：二进制的是“传输”，文本的是“存储与审计”。不要为了减量把所有 JSON 都转 proto——只会引入没人想维护的序列化层。**

## 5. 衍生产品（未来思考）：出生即 gRPC

未来的新服务（包括所有围绕当前系统的衍生品），默认契约直接定成 gRPC + proto：

| 未来产品 | 建议传输形态 |
|----------|--------------|
| 移动端推送网关 | 对外走第三方通道（APNs/FCM），对内 gRPC 收事件 |
| 数据中台 / 埋点收集 | 入口 gRPC 流式上报（批量+压缩），比 HTTP 上报省一个量级 |
| AI 网关（多模型路由） | gRPC 流式（server-streaming），SSE 只留给浏览器出口 |
| 直播流控 / 弹幕扇出 | gRPC 长连接 + 二进制帧，替代每条 JSON 消息 |
| 运营后台管理面 | gRPC-Web 或 JSON，取决于前端框架 |
| 内容审核流水线 | gRPC 任务队列 + proto 结构，天然可加字段不断言 |

统一的做法：

1. 建立**中心 proto 仓库**（`proto/` 目录），唯一事实来源
2. proto 文件**版本化管理**（buf/Bazel），生成代码纳入 CI
3. 新 service 从 `buf` 模板生成，**不再手写 HTTP handler**
4. proto 字段号一旦发布**永不重排**（兼容扩展）

## 6. 当前代码落地清单

不写空话，落到这个仓库的具体改动点：

| 改动 | 现状 | 去向 |
|------|------|------|
| 内部 `ServiceCaller` | memory / http / grpc 三种实现 | 统一走 `grpc` type，删 http impl |
| 内部模块间调用 | 部分走 HTTP handler | 全改 gRPC client 直呼 |
| 新增服务契约 | 手写 `.proto` + 生成 | 全部加 proto，HTTP handler 只作对外壳 |
| SSE 推送（弹幕/通知） | `/sse/*` HTTP | 保留（浏览器消费），内部发布改 gRPC 流 |
| 列表接口 | 全量 JSON | 加 pagination / field_mask，按需裁剪 |
| 指标/计数 | JSON 里每轮全传 | 拆分接口 + 聚合字段精简 |

## 7. 风险与反对意见（诚实声明）

| 顾虑 | 回应 |
|------|------|
| 浏览器不能用 gRPC | 对，所以对外边界保留 HTTP/JSON |
| 调试不方便（二进制看不懂） | grpcurl + buf 风格调试工具，配合 `--json` 转码 |
| proto 一旦发布难改 | 字段号纪律 + proto 兼容规则，可加不可删 |
| 工具链重 | 一个 buf + 生成脚本，一次搞定 |
| HTTP/2 单连接有队头阻塞 | HTTP/3 已在路上，gRPC 生态会跟进 |

---

## 8. 最后结论

- **传输减量靠三件事：Protobuf、字段裁剪、HTTP/2 复用。协议本身只是载体。**
- **内部一律 gRPC；对外 JSON 是边界，不是偷懒。**
- **未来每个衍生产品出生即 gRPC + proto，统一契约管理，从源头避免再次割裂成"一堆各说各话的 JSON 服务"。**
- gRPC 让"传输变轻"，只有配合"结构变契约"才真正解决长尾问题。
